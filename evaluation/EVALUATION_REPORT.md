# Lumina: evaluation report

This is the evaluation of Lumina, an alumni network and mentorship platform for former
Kenya Airways (KQ) employees. It covers five areas: semantic mentor matching, performance,
event-driven re-indexing, consent and recommendation correctness, and usability (prepared,
not yet run). Every number below comes from a script in this repository and a file in
`evaluation/results/`; [`README.md`](README.md) gives the commands to reproduce it. All
profiles are synthetic, so the results describe the system's behaviour on fictional data,
not its performance on real KQ alumni.

## 1. Setup

| Item | Value |
| --- | --- |
| Dataset | 200 synthetic former-KQ profiles across 12 departments, with work histories (`data/synthetic_alumni.csv`) |
| Mentor corpus | 169 profiles consent to matching; 133 of these are also available: the **eligible corpus** for every matching run |
| Queries | 22 labelled career queries: 12 *domain* (name a former-department area), 10 *career-transition* (describe a move whose answer depends on where a mentor works now) |
| Relevance labels | Rule-based from structured fields (department, skills, current industry, organisation, title), frozen in `relevance_labels.json` before evaluation |
| Embedding model | `BAAI/bge-base-en-v1.5` (768 dimensions), pre-trained, inference only; not trained or fine-tuned |
| Retrieval | Exact cosine similarity in PostgreSQL 17 + pgvector; similarity threshold 0.50; k = 5 |
| Machine | GitHub Codespaces VM: 4 vCPU (AMD EPYC 7763), 15.6 GB RAM, Linux 6.8; Node.js 24.21, Python 3.14; web app (production build), matching service, PostgreSQL, Kafka and test clients all on this one machine |

## 2. Method

**Matching quality.** Each query is answered by three systems over the same eligible
corpus: **semantic** (the production system: BGE query embedding, exact cosine in
pgvector, threshold 0.50), a **keyword** baseline (TF-IDF over the identical profile
text), and **hybrid** (the semantic candidates re-ordered by BM25 through reciprocal-rank
fusion). Metrics are Precision@5, Recall@5, F1@5 and reciprocal rank of the first
relevant result (MRR@5), macro-averaged over queries. Uncertainty is shown with
percentile bootstrap 95% confidence intervals (10,000 resamples of queries), and
differences are tested with two-sided paired Wilcoxon signed-rank tests. A sensitivity
analysis repeats the semantic run at thresholds 0.40–0.65 without changing production.
An off-topic query ("Astrophysics research on black holes…") is a negative control.

**Correctness.** The live service's answers are compared with an independent
re-computation: the same BGE model loaded separately, with exact cosine similarity computed in
NumPy over the vectors stored in PostgreSQL, applying the documented eligibility, threshold
and ordering rules. Exclusion is probed adversarially. Each excluded mentor's own
headline is used as a query, which would rank that mentor near the top if the filter
leaked. The same probe on eligible mentors acts as a control. Explanations are generated by the app's own code
(`explainMatch`) and each sentence is checked against the mentor's stored attributes.

**Event-driven re-indexing.** A disposable mentor is created and edited through the same
transactional writes the web app performs (row change plus outbox row). The real worker
(`scripts/run_profile_events.py`) relays the change to Kafka and re-embeds it. The harness
measures time to publish, re-embed and rank first in live search, and deliberately
injects duplicates, a malformed event, a Kafka outage, a worker outage, a worker started
before Kafka, consent withdrawal and an availability change.

**Performance.** A Node.js harness signs in a temporary verified member and measures:
mentor search directly against the matching service, and end to end through the
web app's API, 22 queries × 5 rounds each. It also measures five ordinary pages plus the
Home page, 20 times each, first with no matching load and then while 1, 4 and 8 clients
search continuously. Every request is kept, including any errors. Five warm-up rounds
are excluded and labelled as such.

**Automated tests.** All suites run with live PostgreSQL, Kafka and the matching service
(`scripts/evaluate_test_suites.sh`).

## 3. Results

### 3.1 Semantic matching quality

| Query set | System | P@5 | R@5 | F1@5 | MRR@5 |
| --- | --- | --- | --- | --- | --- |
| All (22) | **Semantic (BGE + pgvector)** | **0.827** [0.700, 0.936] | **0.476** [0.384, 0.574] | **0.567** [0.483, 0.642] | **0.898** [0.773, 1.000] |
| All (22) | Keyword (TF-IDF) | 0.773 [0.627, 0.900] | 0.410 [0.332, 0.485] | 0.510 [0.419, 0.595] | 0.849 [0.712, 0.955] |
| All (22) | Hybrid (BGE + BM25) | 0.809 [0.682, 0.918] | 0.463 [0.374, 0.556] | 0.552 [0.469, 0.626] | 0.856 [0.727, 0.955] |
| Domain (12) | All three systems | 1.000 | 0.475 | 0.637 | 1.000 |
| Transition (10) | **Semantic** | **0.620** | **0.477** | **0.482** | **0.775** |
| Transition (10) | Keyword | 0.500 | 0.331 | 0.358 | 0.667 |
| Transition (10) | Hybrid | 0.580 | 0.449 | 0.451 | 0.683 |

*Brackets: bootstrap 95% confidence intervals. Source: `results/matching/comparison.csv`; Figure 4.1.*

- On **domain** queries all three systems are perfect on precision (P@5 = 1.000) and
  identical on every metric: the query names the department vocabulary, so meaning and
  keywords agree.
- On **career-transition** queries the semantic system leads on every metric:
  F1@5 +0.125 and MRR@5 +0.108 over keyword. It has the higher F1 on 6 of the 9 queries
  where the systems differ, and keyword is higher on 3 (Figure 4.2). With only 10 such queries the
  difference is **not statistically significant** (Wilcoxon p = 0.20 for F1@5, p = 0.63
  for MRR@5; `results/matching/significance.csv`).
- **Hybrid** never beat semantic on any macro metric, so semantic ranking was kept in
  production.
- R@5 cannot exceed 0.569 on average, because many queries have more than five relevant mentors.
  The semantic system reaches 0.476, which is 84% of that ceiling.
- **Failure case.** "I want to leave aviation and work in a bank" scored F1@5 = 0. The
  model returned mentors from KQ's *Finance department*, not people who now work in
  *banking*: semantic similarity matched the topic but not the career destination.
- **Negative control.** The off-topic query returned 0 results in all three systems.
- **Threshold.** Results are identical at 0.45 and 0.50 (P@5 0.827, five results per
  query, control 0). At 0.40 the off-topic control returns 5 mentors. At 0.55 and above,
  real queries start losing results: at 0.60 P@5 falls to 0.518 and 9 queries return
  nothing. So 0.50 sits on the stable plateau between admitting off-topic matches and
  losing relevant ones (Figure 4.3, `results/matching/threshold_sweep.csv`).

### 3.2 Consent and recommendation correctness

| Check | Result |
| --- | --- |
| Service ranking equals the independent exact re-computation (22 queries + control, k = 5 and k = 50) | **46 / 46 identical** (ids, order, scores within 10⁻⁴) |
| Distinct mentors returned in the whole run that were not eligible | **0** of 133 returned (69 profiles excluded) |
| Consenting-but-unavailable mentors returned for a query built from their own headline | **0 / 36**, although all 36 would rank in the top 5 without the filter |
| Mentors without consent (31): embeddings left in the index / returned | **0 / 0** |
| Control: eligible mentors found for their own headline | 36 / 36 in the top 5 (29 at rank 1) |
| Similarity threshold (5 thresholds × 23 queries) | 0 scores below threshold; results nested in every case |
| top-k (5 values × 23 queries) | never over the limit; always a prefix of the longer list |
| "Mentors for you" recommendations (40 members) | never the member themselves, never an excluded or ineligible mentor, all ≥ 0.60 |
| Explanation sentences grounded in stored profile attributes | **266 / 266** (110 results; 2.4 reasons each) |
| Overlap reasons confirmed by an independent tokenizer | 226 / 226; the other 40 are fallback statements of the mentor's roles |

*Sources: `results/correctness/summary.json`, `explanations_summary.json` and the CSVs beside them.*

### 3.3 Event-driven re-indexing (PostgreSQL outbox → Kafka → worker → pgvector)

| Scenario | Outcome | End to end |
| --- | --- | --- |
| New mentor profile | published, embedded, ranked first for its topic | 8.1 s (first event loads the model) |
| Profile updated | new topic ranked first; old topic no longer returns it | 0.7 s |
| 8 duplicate events (5 outbox rows + 3 raw re-deliveries) | exactly one embedding, not re-computed (idempotent) | — |
| Malformed event, then a real change | skipped, worker kept running; change applied | 0.9 s |
| Kafka stopped for 20 s while a change was saved | change held in the outbox, index unchanged, worker stayed up; applied after the broker returned | 0.9 s after the broker was reachable (7.8 s after restart began) |
| Worker stopped while a change was saved | change waited in the outbox; applied when the worker restarted | 7.1 s (includes model load) |
| Worker started while Kafka was down | **failed before the fix** (process exited); after the fix it waited and processed the change | 10.7 s |
| Consent withdrawn / given again | hidden from search in 0.13 s, embedding deleted in 0.4 s; re-indexed on renewal | 1.1 s |
| Marked unavailable / available | hidden in 0.13 s, embedding kept; visible again in 0.11 s without re-embedding | — |
| Cleanup | fixture removed; every other embedding byte-identical | — |

All **18 / 18** checks passed. Median change-to-search time was **1.1 s** (range 0.7–10.7 s
over 7 propagations). Source: `results/event_pipeline/`; Figure 4.5.

### 3.4 Performance

Measured 2026-11-17 on the production build, with the machine otherwise idle (CPU 80% idle
immediately before the run). **1,069 recorded requests, 0 errors, 0 timeouts.**

| Request | Load (concurrent mentor searches) | Requests | Mean | Median | p95 |
| --- | --- | --- | --- | --- | --- |
| Mentor search, matching service directly | idle | 110 | 92.9 ms | 89.1 ms | 119.3 ms |
| Mentor search through the web app | idle | 110 | 109.1 ms | 104.7 ms | 151.2 ms |
| Mentor search through the web app | 1 | 56 | 153.4 ms | 142.3 ms | 224.7 ms |
| Mentor search through the web app | 4 | 117 | 496.7 ms | 514.3 ms | 589.5 ms |
| Mentor search through the web app | 8 | 196 | 942.1 ms | 958.1 ms | 1,051.5 ms |
| Ordinary pages (5 pages × 20) | idle | 100 | 16.4 ms | 15.0 ms | 26.6 ms |
| Ordinary pages | 1 | 100 | 25.2 ms | 23.0 ms | 41.8 ms |
| Ordinary pages | 4 | 100 | 22.5 ms | 21.7 ms | 35.1 ms |
| Ordinary pages | 8 | 100 | 21.6 ms | 20.4 ms | 36.3 ms |
| Home page (includes "Mentors for you") | idle | 20 | 116.7 ms | 115.5 ms | 124.6 ms |
| Home page | 8 | 20 | 923.9 ms | 907.8 ms | 997.4 ms |

| Concurrent searches | 1 | 4 | 8 |
| --- | --- | --- | --- |
| Throughput (searches per second) | 6.5 | 8.0 | 8.4 |

*Sources: `results/performance/summary.csv`, `pages_idle.csv`, `throughput.csv`, every request in
`latency_samples.csv`; Figure 4.4.*

- An idle mentor search takes about **0.1 s**. The web app adds about 16 ms to the
  matching service, for session checks, the consent re-check and logging.
- **Ordinary pages stay fast under matching load.** Their median rose from 15 ms to about
  20–23 ms, and p95 stayed under 42 ms at every load level. Mentor search does not slow
  down browsing.
- **Mentor search queues under concurrency.** Latency grows almost linearly with the
  number of simultaneous searches while throughput levels off at about 8.4 searches/s. The
  service serialises model inference behind one lock (`services/matching/app/main.py`), so
  this is the capacity of one service instance on this machine. The Home page shows the
  same effect, because it asks the matching service for recommendations.
- Scaling therefore means running more matching-service instances, or batching
  inference. The web tier is not the constraint.

## 4. Changes made during the evaluation

The matching algorithm, threshold and model were not changed. Defects found while testing were fixed and are listed here:

| Change | Why | Verified by |
| --- | --- | --- |
| `services/matching/app/profile_events.py`: Kafka set-up (topic, producer, consumer) is retried with back-off instead of exiting | The worker crashed (`KafkaTimeoutError`) when started before Kafka, for example after a reboot, so profile changes were not indexed until someone restarted it | 3 new unit tests; live scenario S7 |
| `services/matching/tests/test_profile_events.py`: live-broker test ignores records it did not write | The test read the whole shared topic and assumed every record was valid JSON; after the harness injected a malformed event (which the worker correctly skips), it crashed | worker tests 10/10 with live Kafka |
| `tests/registry/test_registry_tools.py` and `data/synthetic_alumni_registry.csv`: 50 → 200 fixtures | Tests and fixture file were not updated when the dataset grew to 200; the database already held 200 | registry tests 4/4 |
| `next.config.ts` + `SERVER_ACTIONS_ALLOWED_ORIGINS`; `scripts/setup_env.py` | Through GitHub Codespaces port forwarding every form (sign-in, Google, profile saves) failed with HTTP 500, because the proxy rewrites the `Origin` header | sign-in through the Codespaces URL |
| `scripts/evaluate_matching.py` extended | Per-query CSVs, confidence intervals, significance tests, threshold analysis; guards against non-synthetic mentors entering the corpus | rerun reproduces the original published averages exactly |
| New evaluation scripts | `evaluate_correctness.py`, `evaluate_explanations.mjs`, `evaluate_event_pipeline.py`, `evaluate_performance.mjs`, `evaluate_test_suites.sh`, `evaluation_charts.py`, `render_charts.mjs`, `score_sus.py` | outputs in `results/` |

During development of the harness itself, one defect was in the harness (UUID objects
compared with string ids); it was fixed before the reported run.

## 5. Limitations

- **Synthetic data.** Profiles and biographies are generated from templates; labels come
  from structured fields, not independent human judgement. Real profiles are messier, which
  probably helps semantic matching relative to keywords but lowers absolute scores.
- **Small query set.** 22 queries (10 transition) give wide confidence intervals; the
  semantic advantage on transition queries is consistent but not statistically significant.
- **Single machine.** Latency was measured with the web app, matching service, database,
  Kafka and load generator sharing one cloud development VM; absolute numbers indicate
  relative behaviour, not production capacity. The matching service serialises model
  inference behind one lock, so concurrent searches queue.
- **One run per event scenario.** Propagation times are single measurements.
- **Not evaluated:** real alumni data, a production cloud deployment, Google OAuth consent
  (external; only the redirect is tested), and usability (prepared, not run).
